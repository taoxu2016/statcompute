# Decisions

Proposed by the assistant; taken by the maintainer. Numbers are never reused.

| ID | Decision | Status |
|---|---|---|
| D-01 | The repository is named `statcompute`. It holds the research workspace, the benchmark of all implementations and the new engine | Approved 2026-11-14; pushed to https://github.com/taoxu2016/statcompute |
| D-02 | Licence: MIT, as the reference packages | Approved 2026-11-14. LICENSE added in round 3; the copyright holder is Tao Xu |
| D-03 | Target runtime: Databricks Runtime 17.3 LTS, which is Apache Spark 4.0.0 with Scala 2.13. pprof_spark targets Spark 4.1.0 and Runtime 18 | Approved 2026-11-14 |
| D-04 | The engine's language and determinism are decided after the baseline, not before. Two candidates are measured side by side in step 0: JVM kernels with bitwise partition invariance (pprof_spark's rule NN-4, the feasibility study's route), and NumPy kernels inside Spark partitions (`lab_spark`), which are simpler and use BLAS but are not bitwise reproducible | Approved 2026-11-14; the choice itself is still open |
| D-05 | Prototypes stop when the next Newton step is below 1e-8 standard errors (1e-10 for "tight"): the tolerance class T_CONV of the research roadmap (F-10). The bound is provisional until calibrated | Approved 2026-11-14 |
| D-06 | Numerical comparisons take pprof_py at its tightest tolerance as the reference | Approved 2026-11-14 |
| D-07 | The repository stores run records and reports of synthetic data only, as JSON and Markdown. Since the repository is public, records are scrubbed when written: the cluster identifier is hashed, and e-mail addresses and user folders are removed from messages and traces | Approved 2026-11-14; the scrubbing was added in round 2 |

| D-08 | The engine is Python on Spark: NumPy kernels inside partitions that hold whole strata or providers (`statcompute.engine`). This settles D-04. Reasons: on the production cluster the prototype of this design gave the same estimates as pprof_py and was faster than pprof_spark for the logistic model; its kernels use memory outside the 2.2 GB JVM heaps that Photon leaves; it needs no JAR build; it can be tested end to end in the assistant's sandbox; and pprof_spark's own project is already pursuing the JVM route. Cost: results are reproducible bit for bit only for a fixed layout and session, and to rounding otherwise | Proposed 2026-11-16; the engine's first version is built on it |
| D-09 | A Cox estimate agrees with pprof_py's when the two differ by the Newton step that remains at pprof_py's estimate; the harness is to report that step beside the difference. Reason: pprof_py halves its last step whenever rounding makes the log-likelihood come out lower, at any tolerance, so D-06 does not make its estimate the root (`docs/spec/engine.md`, section 5.3; 4.3e-5 standard errors on the cluster's 100-feature data). The tests have compared this way since round 5. Cost: one evaluation at the reference's estimate per comparison; until the harness has it, its agreement table shows such a fit as over T_COEF | Proposed 2026-11-19 |
| D-10 | Without strata the working set is laid out like the other two: ceil(rows / `rows_per_partition`) partitions, the rows placed by row identifier and sorted by it. Reasons: the fit no longer inherits the input's partitions (17 and 33 on the cluster, for 40 cores), and with `row_id` it returns the same bits whatever the input's layout. Cost: a shuffle and a sort when the working set is built, which a fit without strata did not have, and one pass-1 table per partition to the driver in every evaluation (OI-26). `partitions="input"` keeps the earlier layout | Proposed 2026-11-19; round 12 implements it as the default. On the cluster on 2026-11-20, four runs: 14 to 18 effective cores instead of 7 to 12, calls not clearly faster, and a new shuffle when an executor was lost (`docs/reports/2026-11-20-databricks-round-12.md`) |
| D-11 | Times the engine reports: "prepare" ends when the working set exists, so for Cox it contains the first evaluation, which is the pass that builds it; "fit" is the evaluations after it; every evaluation's time is recorded. Reason: one job fewer means the build has no job of its own to time. Cost: "fit" in a Cox record from round 12 on is one evaluation shorter than in earlier records, so across versions only whole calls compare | Proposed 2026-11-19; round 12 implements it |
| D-12 | pprof_py remains the statistical specification, but it is not unquestionable computational ground truth. statcompute validates results independently and reports potential issues; a change of methodology is reviewed explicitly | The maintainer's, 2026-11-20. Issues found are kept in `docs/reference-issues.md`. D-06 is read with this: pprof_py at its tightest tolerance is what estimates are compared with, not the definition of their last digits |
| D-13 | Algorithms flow from statcompute to both pprof_py and pprof_spark; validation and benchmark evidence flow back. The goal: statcompute is a reusable platform for computational research and development whose validated algorithms benefit both packages | The maintainer's, 2026-11-20, with the division of responsibilities now in `docs/architecture.md` |
| D-14 | Bitwise reproducibility is not an absolute requirement. Agreement within strict numerical tolerances, together with stable provider-level flags and auditable execution configurations, may be sufficient | The maintainer's, 2026-11-20. It removes the main cost recorded against D-08, which stays the maintainer's to take. D-15 and D-16 propose what the second and the third condition mean |
| D-15 | Stable provider-level flags, defined. Two computations of the same fit may flag a provider differently only when its two statistics are within T_FLAG of each other: 1e-7 for a z statistic, 1e-9 for a p-value. Such a provider is borderline and is reported; any other difference in a flag is a numerical disagreement. A run record keeps, per test, the counts, a digest of the flags and the smallest distance of a statistic from its cut-off. Reason: a flag is a cut-off on a continuous statistic, so no tolerance on the statistic can promise equal flags, and among 8,000 providers and many runs one will sit on a cut-off some day. Evidence: probe A-10. Not decided here: whether a production report shows borderline providers, which is methodology | Proposed 2026-11-20. `statcompute.validation.flags` computes it and the engine's logistic records carry the summary; nothing passes or fails by it yet |
| D-16 | The execution record, defined: what is kept with a fit so that its digits can be audited. The data's identity and row count; the package version; every setting of the estimator; the layout (partitions, rows per partition, how rows are placed, the row identifier, the Arrow batch size); Spark's version and runtime; Python, NumPy and the BLAS library on the driver and on the executors; iterations, evaluations and the last Newton step | Proposed 2026-11-20. `docs/spec/reproducibility.md` says what the harness records already and what is missing (OI-29) |
| D-17 | A last stage for an algorithm after "engine": handed over. It leaves statcompute as a written specification, a reference kernel that needs no Spark, and fixtures with expected values, offered to the maintainers of pprof_py and pprof_spark, who apply it. And a register of issues found in the packages this project reads, with the evidence and whether each has been reported | Proposed 2026-11-20. The stage is in `docs/architecture.md`; the register is `docs/reference-issues.md`, with eight entries |

The research roadmap has decisions of its own (its section 9: adopting track A with its amendments,
the definition of the estimate at the bound, the production design facts, the first second-wave
project). Those are not covered by the approval above and stay open.
